# Changelog

## Unreleased

- Repository scaffold added: pnpm workspace with packages `server`, `ui` (placeholder), `packs`, `cli`, and `skill`, strict TypeScript configuration, ESLint flat config, Prettier, Vitest, license compliance checker, and CI workflows.
- Specification, architecture and roadmap added. There is no working release yet and the product described in the documentation is planned.
- Redaction added in `packages/server/src/security/redact.ts`: masks API keys and tokens, passwords, card numbers, email addresses and phone numbers in a string, keeps a SHA-256 hash of the original input for exact match memory lookup, and reports which rules replaced how many values. Implemented and tested as a module; nothing in the server calls it yet.
- MCP server bootstrap added: an MCP server over the stdio transport that lists its tools and serves an `instructions` field from placeholder text, with one tool per file discovered by listing the tools directory. The only tool is `server_status`; the decision tools are planned and not implemented.
- Key storage added in `packages/server/src/security/keys.ts`: provider keys live either in the operating system keychain or, where that is unavailable, in a single AES-256-GCM envelope with its random data key in a separate `0600` file in an injectable directory. No key reaches the database, a log or a response: the settings table is never written by this module, and `summarizeKey` returns a shape with no field a full key could occupy. The encrypted file store and the masking rules are implemented and tested as a module; the keychain backend is experimental, round-tripped by hand on macOS only and unverified on Linux and Windows. Nothing in the server calls it yet.
- `action_guard` tool added: `packages/server/src/tools/action_guard.ts` holds the logic and `packages/server/src/mcp/tools/action_guard.tool.ts` the wire definition. It takes an action, a target element, a URL and an optional redacted snapshot, and answers `allow`, `ask_user` or `block` with a plain reason for the user, the rule ids that produced the verdict, and `decision_id`, `confidence`, `path` and `latency_ms`. The safety rules that need no pack are compiled into the tool, so a payment or destructive action is `ask_user` on a server with no pack loaded; the control text is the text the browser pack carries, in English and in Bangla, and a checkout step whose committing button reads only `Continue` is caught from the URL path. A credential or card number in the text an action would enter, and a command that rewrites history or destroys data, are reported as `block`. A learned pattern may only add caution and never remove it, an unknown action falls back to a low-confidence `allow` with `needs_ai`, and every verdict is logged with `is_safety` set when a safety rule produced it. The verdict is advisory: the output carries `advisory: true`, the reason, the tool description and the served instructions all say so, and nothing here prevents an agent from acting. Nothing the agent sends can turn a safety verdict into `allow`: only `action`, `target`, `text`, `value`, `url` and `snapshot` are read, a `trusted`, `user_approved`, `override`, `confidence` or `verdict` argument is ignored, and exact-match memory is not consulted at all. Implemented and tested by `packages/server/test/action-guard-tool.test.ts`, including eleven synthetic fixtures in `packages/server/test/fixtures/action-guard/` that carry prompt-injection text and a run over a real MCP client on stdio.
- Browser pattern pack v1 added in `packages/packs/browser/`: seven versioned YAML files carrying 33 rules for the seven browser checks (cookie banner, newsletter or promo popup, login wall, captcha, payment, destructive and outbound actions), with Bangla control text on each family, including `অর্ডার করুন`, `কিনুন`, `পেমেন্ট`, `সম্মতি দিন`, `পাঠান` and `মুছুন`. Each rule declares the canonical question it answers, so no rule can answer another check's question, and the payment, destructive and outbound rules are advisory `safety: true` rules that answer `ask_user`. The rules and 65 synthetic fixtures in `packages/packs/browser/fixtures/` are implemented and tested: the fixture suite loads the pack through the loader, runs every fixture through the engine, prints a confusion summary, and requires at least 95 percent correct overall and every payment and destructive fixture correct. The fixtures are hand written to resemble real accessibility trees and are not captures of real sites, so that figure measures internal consistency and not accuracy on real pages. The `action_guard` tool serves these three risky families and is implemented and tested; the `page_check` tool that would serve the other four is planned and not implemented.
