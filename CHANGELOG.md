# Changelog

## Unreleased

- `page_check` tool added in `packages/server/src/tools/page_check.ts` and served as `page_check`: one call reports `page_type`, `popup` with its close control when a rule names one, `login_wall`, `captcha` and `risky_actions[]` from a URL and a redacted accessibility tree or DOM snapshot, each part carrying its own `decision_id`, `confidence`, `path` and `latency_ms`. Implemented and tested by `packages/server/test/page-check-tool.test.ts`. A part no rule answered comes back in `needs_ai` in the shape `decide` uses, so `submit_answers` completes it. Every element is read separately against the risky action question, and an element a rule flags is reported with its element text, its risk kind and the rule id that flagged it; an element no rule flags produces no decision row, because no question was asked about it. Snapshot text goes through redaction before storage and the reported element text is redacted on the way out. The work is bounded (400 elements, 256 characters of element text, 8192 characters of page text, 50 reported risky actions); the bounds are reported on every call and anything cut is counted, never silent. The browser pack is loaded through the pack loader at server start-up, and a pack that fails to load does not stop the server: the rules that did load are served and `packs.errors` names the pack that did not. Measured on a fixture page: median 1.5 ms and mean 1.2 ms per call over 40 calls on an idle machine, and a 267KB snapshot at a mean of 12.9 ms per call over 10 calls. Page content is data: a snapshot whose text says to ignore the rules answers exactly as one that does not, and a test says so. The safety check is advisory and unchanged: a risky action is a request for the user and nothing in this tool prevents an agent from acting. No rule in the shipped browser pack targets the page type question, so the page type comes back in `needs_ai` in this build, and no rule names a popup close target, so `close_target` is `null` until a pack declares the `close_target` matcher. Accuracy on real pages is unverified: the browser pack is measured only on synthetic fixtures.

- Repository scaffold added: pnpm workspace with packages `server`, `ui` (placeholder), `packs`, `cli`, and `skill`, strict TypeScript configuration, ESLint flat config, Prettier, Vitest, license compliance checker, and CI workflows.
- Specification, architecture and roadmap added. There is no working release yet and the product described in the documentation is planned.
- Redaction added in `packages/server/src/security/redact.ts`: masks API keys and tokens, passwords, card numbers, email addresses and phone numbers in a string, keeps a SHA-256 hash of the original input for exact match memory lookup, and reports which rules replaced how many values. Implemented and tested as a module; nothing in the server calls it yet.
- MCP server bootstrap added: an MCP server over the stdio transport that lists its tools and serves an `instructions` field from placeholder text, with one tool per file discovered by listing the tools directory. The only tool is `server_status`; the decision tools are planned and not implemented.
- Key storage added in `packages/server/src/security/keys.ts`: provider keys live either in the operating system keychain or, where that is unavailable, in a single AES-256-GCM envelope with its random data key in a separate `0600` file in an injectable directory. No key reaches the database, a log or a response: the settings table is never written by this module, and `summarizeKey` returns a shape with no field a full key could occupy. The encrypted file store and the masking rules are implemented and tested as a module; the keychain backend is experimental, round-tripped by hand on macOS only and unverified on Linux and Windows. Nothing in the server calls it yet.
- Browser pattern pack v1 added in `packages/packs/browser/`: seven versioned YAML files carrying 33 rules for the seven browser checks (cookie banner, newsletter or promo popup, login wall, captcha, payment, destructive and outbound actions), with Bangla control text on each family, including `অর্ডার করুন`, `কিনুন`, `পেমেন্ট`, `সম্মতি দিন`, `পাঠান` and `মুছুন`. Each rule declares the canonical question it answers, so no rule can answer another check's question, and the payment, destructive and outbound rules are advisory `safety: true` rules that answer `ask_user`. The rules and 65 synthetic fixtures in `packages/packs/browser/fixtures/` are implemented and tested: the fixture suite loads the pack through the loader, runs every fixture through the engine, prints a confusion summary, and requires at least 95 percent correct overall and every payment and destructive fixture correct. The fixtures are hand written to resemble real accessibility trees and are not captures of real sites, so that figure measures internal consistency and not accuracy on real pages. The `page_check` and `action_guard` tools that would serve these rules are planned and not implemented.
